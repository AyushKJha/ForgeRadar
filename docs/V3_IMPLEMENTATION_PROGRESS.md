# ForgeRadar V3 implementation progress

Status is based on code and tests, not design intent. V3 has not been deployed or pushed.

- [x] Phase A — Audit & stability. Audit, architecture, inventory, risk log and recovery procedure written. `backup.mjs` created and a live-data snapshot verified by checksum and SQLite integrity. The daily launcher now uses process-local PowerShell script permission and exits cleanly without duplicate work. Baseline tests: 20/20 passed.
- [x] Phase B — Local free foundation. Versioned SQLite migrations provide job history, a durable pending-command queue and 24-hour source cache. Pending commands resume once after restart; claimed work becomes interrupted and requires review. The next collection time persists. Settings shows actual job/model/source diagnostics and opt-in OpenAlex/Crossref records with separate publication/retrieval dates. Local Ollama remains sequential; low-memory runs are blocked, and existing heuristic discovery/manual planning still work without it. Existing cached data remains available offline. arXiv, full source-wide opt-in controls and advanced manual development remain for later phases.
- [x] Phase C — Local multi-user accounts with isolated profiles, consented manual interests, reviewed PDF/DOCX suggestions, public GitHub portfolio selection, export and deletion. Owner-only legacy APIs remain protected. Remote member access and richer provenance review remain for later phases.
- [ ] Phase D — Discovery intelligence. In progress: per-user research feed applies a hard selected/excluded-domain filter, offers six explicit modes and mode weights, separates publication from retrieval age, explains heuristic weights, and has an honest empty state. Manual opt-in OpenAlex/Crossref scans send only selected domain names. Account-scoped save/dismiss/restore and 2–5 source comparison work. Local saved/irrelevant feedback now makes small, capped, visible score adjustments without relaxing eligibility; users can reset each signal. Related-work view searches locally cached research titles and GitHub repository signals, with limited-coverage disclosure. Fuller battle criteria and skill gap remain.
- [ ] Phase E — Project studio, tasks and agents. In progress: source-grounded or user-defined local proposal drafts are editable and require an explicit approval action. Approved proposals support account-scoped persistent manual tasks with create/edit/status/delete and acceptance/evidence gating. Typed task dependencies, cycle prevention, blocking rules and per-task history now persist. Review-only suggestions use a selected installed local Ollama model, a 120-second timeout, five-task limit, duplicate filtering and a free-RAM guard. A confirmed local build can generate a bounded Node + SQLite data workspace, run syntax and CRUD acceptance tests, store the result and activate an authenticated private preview. This is a real but limited data-app build path, not arbitrary agent software development. A real qwen3:4b task-planner smoke run produced suggestions but omitted one rationale, so the UI exposes that omission; a second run was blocked at 1.0 GiB free RAM by the 1.2 GiB guard. A live local-model app build, cancellation, architecture canvas and broader agent execution remain. Task estimates, due dates, archive/restore and blockers now persist.
- [ ] Phase F — Validation evidence and protected remote access. Generated data-app builds now run real syntax and persistent CRUD acceptance tests before an account-scoped preview is activated. Preview HTML, JavaScript, CSS and API require the owning account. Exact-host HTTPS tailnet proxy support keeps the app on loopback, uses account authorization and secure cookies, and has simulated host/origin/isolation tests. [Private access setup](PRIVATE_REMOTE_ACCESS.md) documents the free Tailscale Serve path. Tailscale is not installed or activated, real cross-device access is unverified, and the broader project validation lab remains.
- [ ] Phase G — Explicit public publication workflow. Release review scans the actual generated file tree for platform branding, secret patterns, unexpected files and README sections, displays SHA-256 hashes, checks outstanding tasks, and marks human/hosting review. A separate owner-only final action uses an exact file fingerprint, reviewed repository name and explicit confirmation. Its code creates a private GitHub repository first, pushes without force, verifies the remote commit, then changes visibility to public and verifies it; failure before that leaves the repository private and records the partial state. The GitHub path passed mocked integration tests but has not been exercised with a real V3 project or public repository. Dynamic Node + SQLite apps get a code URL only; GitHub Pages is not offered as a functioning backend. Website deployment, maintenance updates and rollback remain.
- [ ] Phase H — Eclipse product experience (owner's latest direction overrides the earlier two-theme requirement). The V3 login now has a working sliding sign-in/sign-up card inspired by the owner's reference, a skippable first-visit intro, mobile layout and reduced-motion support. Eclipse is the main login on port 4317. Profile entry now uses a two-column dark neumorphic layout, compact horizontal navigation, selectable domain tiles and collapsible optional fields; existing data bindings and import actions remain. The theme selector is removed, old theme values migrate to Eclipse without losing reduced-motion preferences, and the workspace has an accessible constellation based on real matched sources. Previews and further mobile polish remain.

New accounts automatically see a host-local AI readiness check on onboarding. Existing Ollama models are available to every signed-in account; if none exist, the screen gives a RAM-based suggestion and the exact manual host setup command. A browser cannot install software on a visitor's device, and model downloads are not started silently. Manual planning remains available.

The full 2026-10-16 suite passed 54/54 with localhost access, including the mocked GitHub release sequence and real generated-app acceptance tests. `npm` is unavailable in the current runtime, so tests run directly with Node. A verified backup preceded the live schema 10 migration; the local engine still reports 2 existing projects, 129 signals and automation paused. No real V3 app build or public release has been run against the live owner account.
